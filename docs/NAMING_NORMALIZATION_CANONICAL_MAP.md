One row per concept. Schema: `.claude/contracts/canonical-map-entry.schema.json`. Owner: `mission-orchestrator` (arbitrates conflicts via a `conflict-record` + `decision-record`); no agent invents a canonical name independently (`.claude/rules/naming-canonical.md`).

Source of decisions: `/NAMING_NORMALIZATION_DISCOVERY_LOG.md` (repo-root, untracked) is the earlier discovery/decision narrative. This file is the queryable registry. Reconstructed 2026-09-20 during the final naming-closure mission by comparing live entities/DTOs/services/frontend/DB (not by trusting either the discovery log or the previous version of this table, both found stale — e.g. `documents` had been `done` for weeks while still marked `migrating` here, and several "not yet in this table" concepts had already been closed).

Status values used below: `DONE`, `LEGACY_ALIAS_INTENTIONAL`, `LEGAL_DOMAIN_INTENTIONAL`, `NEEDS_DATA_RECONCILIATION`, `NEEDS_PRODUCT_DECISION`, `DEAD_SCHEMA`, `BUG` (fixed, tracked for the record), `HISTORICAL_ONLY`.

## Brazilian fiscal/legal terms — LEGAL_DOMAIN_INTENTIONAL (closed by documentation, not translation)

Per `20260918000045_RenameValorFieldsOnInvoices.ts`'s own header (the policy was already decided and executed for the `valor`-prefixed subset; this registers it formally for the rest of the cluster): these are official Brazilian tax/legal terms with no precise English equivalent. Translating the **identifier** (not just the label) would reduce precision for anyone auditing tax compliance. Display labels are already PT-BR via `field-labels.pt-br.ts`, independent of this decision.

**KEEP_LEGAL_PT_IDENTIFIER, no code change**: `cpf`/`cpf_encrypted`, `cnpj`/`cnpj_encrypted`, `cpf_cnpj`/`cpf_cnpj_encrypted` (polymorphic PF/PJ tax ID — the PF/PJ distinction is real and drives validation), `cfop`, `iss`/`issqn`/`aliquota_iss`/`iss_retido`, `pis`, `cofins`, `inss`, `ir`/`ir_amount` (register an explicit `IRRF` alias in this map, not a rename), `csll`, `base_calculo`, `aliquota`, `natureza_operacao`, `codigo_servico_municipal`, `codigo_municipio`, `inscricao_estadual`/`inscricao_municipal`, `regime_tributario`/`simples_nacional`/`lucro_presumido`/`lucro_real`, `nfse`/`nfe`/`nfce`/`tipo_nota`, `serie`, `tomador` (root term — the legal service-recipient/payer-of-record role in an NFS-e, distinct from a generic "customer"), `prestador` (service-provider role), `tomador_uf` (UF is an official Brazilian state-code designator), `tomador_cep` (CEP is an official postal-code designator), `numero_nota_fiscal` root (`nota_fiscal`).

**NORMALIZE_TECHNICAL_EN_WITH_PT_DISPLAY — DONE (2026-09-23), Cluster F**: `invoices.tomador_endereco`→`tomador_address`, `invoices.tomador_cidade`→`tomador_city` (migration `20260923000001_RenameInvoiceTomadorGenericFieldsToEnglish`; the `tomador_` root itself, `tomador_uf`, and `tomador_cep` stay LEGAL_DOMAIN_INTENTIONAL, untouched). `tomador_email` was already EN, no action. Propagated through entity, DTO, `report-form-contracts.ts`, `field-labels.pt-br.ts`, `form-field-dto-parity.spec.ts`, and every `apps/web/src/modules/accounting` consumer (the invoice form's own field names ARE the wire contract 1:1, no PT-internal boundary layer like leads has).

`numero_nota_fiscal` does **not** exist on `invoices` — the mission's original scope assumed it did. The only `numero_nota_fiscal` column in the whole schema lives on `inventory_items` (a fully-Portuguese-named table: `quantidade`/`localizacao`/`responsavel`/`setor`/`local_compra`/...), tracking a purchase receipt number for physical equipment, unrelated to the NFS-e/billing module this cluster targets. Renaming just that one column's prefix there would be an isolated, inconsistent change against an otherwise all-PT table — out of this cluster's scope, not executed.
